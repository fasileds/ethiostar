# 0013 — Supabase as the database platform

**Status:** Accepted · 2026-08-12
**Amends:** [0002](0002-drizzle-over-prisma.md), [0005](0005-postgres-rls-as-defence-in-depth.md), [0008](0008-background-jobs.md)
**Supersedes:** [0010](0010-custom-session-auth.md) → see [0014](0014-supabase-auth.md)

## Context

Client direction: the database is Supabase.

Supabase is not only a hosted Postgres. It is Postgres plus GoTrue (auth), Storage, PostgREST,
Realtime, and an opinionated role model (`anon`, `authenticated`, `service_role`) with RLS as the
primary access-control mechanism. Adopting it as "just the database" while ignoring the rest produces
the worst outcome: paying its constraints without taking its benefits.

## Decision

Adopt Supabase as the platform, and take the parts that fit:

| Concern         | Decision                                                                                                                                               |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Database        | Supabase Postgres. Schema design from [04](../architecture/04-database-and-migrations.md) is unchanged — it is standard Postgres.                      |
| Query layer     | **Keep Drizzle** over a direct Postgres connection. Not PostgREST, not `supabase-js` for data access.                                                  |
| Migrations      | **Supabase CLI** (`supabase/migrations/`) as the runner. SQL authored/generated by drizzle-kit, hand-reviewed.                                         |
| Auth            | **Supabase Auth (GoTrue)**. See [0014](0014-supabase-auth.md).                                                                                         |
| Authorization   | Unchanged: permission strings + scope, checked in the use case ([0011](0011-authorization-model.md)). Claims delivered via a Custom Access Token hook. |
| RLS             | Now **native**, keyed on `auth.uid()`. Still defence in depth, not the only control.                                                                   |
| File storage    | **Supabase Storage** behind the existing `FileStorage` port. Virus scanning stays ours.                                                                |
| Background jobs | **Unchanged** — our Node worker against `job_queue`. Not Edge Functions.                                                                               |
| Realtime        | Adopted narrowly, for three screens. Not a general data-fetch mechanism.                                                                               |
| Edge Functions  | **Not used.**                                                                                                                                          |

### Extensions confirmed available

`pgcrypto`, `citext`, `btree_gist`, `pg_trgm`, `pg_cron`, `pg_net`. `btree_gist` matters: the
appointment-overlap and effective-date `EXCLUDE` constraints depend on it. `pg_cron` requires a Pro
plan or above on hosted Supabase.

## Consequences

**Positive**

- RLS becomes first-class rather than bolted on: `auth.uid()` and `auth.jwt()` are available in
  policies, and Supabase's tooling, docs and dashboard assume this model.
- Auth, storage and their operational burden (password reset flows, email delivery, MFA enrolment,
  signed URLs, bucket policies) are no longer ours to build and patch.
- Managed backups, PITR, read replicas and preview branches without building the tooling.
- Local development parity: `supabase start` runs the full stack in Docker, so what runs locally is
  what runs in production.

**Negative — and these are real**

- **`service_role` bypasses RLS entirely.** Every server-side query issued with it is unprotected. If
  the application uses it by default, RLS is decorative. The mitigation is structural (below) and is
  the single most important rule in this ADR.
- **Connectivity becomes a hard dependency.** With hosted Supabase, the gate and receiving screens
  stop working when the plant's link to the nearest region (Frankfurt / Mumbai) drops. For a coffee
  plant during peak intake this is an operational risk, not a theoretical one. See the open decision
  below.
- **Data residency.** EthioStar holds third-party assets and commercially sensitive customer
  positions. Where that data physically sits is a business decision, not a technical one.
- Supavisor transaction pooling requires `prepare: false` on the Postgres driver — a silent,
  confusing failure if missed.
- Migration ordering moves from our gapless sequence to Supabase's timestamp convention. Reconciled
  in [04 §4.6](../architecture/04-database-and-migrations.md).
- Some vendor coupling: `auth.users`, `storage.objects` and the role model. Contained — the schema is
  ours, Drizzle is portable, and the ports keep storage swappable.

## The structural rule for `service_role`

Non-negotiable, and everything else depends on it:

1. Application requests use a **per-transaction authenticated connection**: `set_config` of
   `request.jwt.claims` plus `set local role authenticated`, exactly reproducing what PostgREST does.
   RLS applies. This is the default path.
2. `service_role` / `postgres` is used **only** by (a) migrations, (b) the background worker, and
   (c) an explicit `system` repository namespace for operations with no user context — and every
   call there is audited.
3. The service-role connection lives in one file, is not exported from it, and is guarded by a lint
   rule plus a CI grep. A second import site is a review failure.

## Open decision for EthioStar — hosted or self-hosted

Both satisfy "the database is Supabase"; the plan supports either and the difference is confined to
[09-operations.md](../architecture/09-operations.md).

- **Supabase Cloud** — managed backups, PITR, branching, no infrastructure to run. Requires a
  reliable link from the plant, and accepts that data resides in the chosen region.
- **Self-hosted Supabase** (Docker, on-prem or a local VPS) — same stack, keeps data and the gate
  screen working on the plant LAN. Costs: you run and back it up yourself, and you lose branching and
  managed PITR unless you build them.

**Recommendation:** start on Supabase Cloud for development and staging, and confirm production
placement after measuring real latency and link reliability from the plant. The application code is
identical either way; only environment variables and the ops runbooks differ. Decide before roadmap
Step 24.

## Alternatives rejected

- **Supabase as "just Postgres", ignoring GoTrue/Storage/RLS.** Pays the constraints, takes none of
  the benefit, and leaves two auth systems to reconcile.
- **`supabase-js` / PostgREST as the data layer.** Cannot express the recursive CTEs, exclusion
  constraints, window functions and partitioned append-only queries this schema needs. It would
  become an escape hatch on every interesting query.
- **Edge Functions for background work.** Fragments the codebase across two runtimes and two
  deployment models for work our Node worker already does durably. See [0008](0008-background-jobs.md).
