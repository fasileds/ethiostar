# 7. Extension Points for Phase 2 and Phase 3

The instruction is precise: leave clean seams, but do not build Phase 2 or Phase 3 functionality,
and do not over-engineer. This document is the ruling on each candidate seam — what we build now,
what we deliberately do not, and the test each decision had to pass.

**The test applied to every item below:**

> Is this something that _cannot_ be added later without changing Phase 1 code or backfilling data
> that was never captured?

If yes, build the seam now. If no, do not — a `ContractPricingStrategy` interface with one
implementation that returns zero is not a seam, it is dead code that will be wrong by the time it
is needed.

---

## 7.1 The four seams that genuinely cannot be retrofitted

These are the ones worth arguing for. Everything else is negotiable.

### Seam 1 — The domain event stream

**Why it cannot wait:** Phase 2 billing must price operational activity, and Phase 3 forecasting,
anomaly detection and the conversational assistant are all built on _accumulated history_. The
document is explicit that Phase 3 "is deliberately placed last because it is built on the
operational record the first two phases create". History not recorded during Phase 1 does not exist
in Phase 2 or 3, and cannot be reconstructed.

**What we build now:** `domain_event` — append-only, versioned envelopes, typed payloads, emitted
for the 25 events in [03-domain-model.md §3.10](03-domain-model.md#310-domain-events-phase-1-catalogue).

**What we do not build:** event sourcing (state is still stored in tables), a message broker, event
replay tooling, projections beyond `stock_balance`.

**Cost of building it now:** ~150 lines plus one table. It is already required for M07's audit
obligation, so the marginal cost of making it a _typed, versioned_ stream rather than a text log is
close to zero.

**How Phase 2 uses it:** M19 subscribes to `ConsignmentReceived`, `KeshaCountConfirmed`,
`ConsignmentStored`, `JobClosed`, `DispatchLoaded` and raises charges. Charges for activity that
happened _before_ M19 shipped can be generated by replaying the stored events — which is only
possible because the events were captured.

**How Phase 3 uses it:** the stream is the training and grounding substrate for M26/M27, and the
audit target for M24's "everything the AI does is audited" requirement.

---

### Seam 2 — Billable-event completeness in operational records

**Why it cannot wait:** M19 prices "unloading, storage days, processing tonnage, bagging, re-bagging,
loading and special handling". If a goods receipt does not record _which activities occurred and at
what quantity_, no amount of later development can bill a receipt from last season.

**What we build now:** the operational records carry every fact a charge would need — quantities in
both units, activity types, timestamps, bag types, locations, dwell start dates. `labour_activity`
already models activity type × quantity × rate for M18, and the same activity taxonomy
(`labour_activity_type`) is what M19 will price against.

**What we do not build:** a `charge`, `charge_line`, `invoice`, `tariff` or `price` table; any
pricing logic; any currency-conversion machinery.

**The specific decision:** `lot.storage_start_date` is set at confirmed receipt in Phase 1, and
`dispatch.departed_at` at gate-out, even though nothing consumes them until M20 computes dwell-time
charging. Two columns. The alternative is Phase 2 guessing dwell time from `created_at`, which is
the day the record was typed, not the day the coffee arrived.

---

### Seam 3 — Approval decisions modelled as data, not booleans

**Why it cannot wait:** M03's workflow engine (Phase 2) must take over routing for approvals that
Phase 1 hardcodes. If Phase 1 stores approval as `is_approved boolean`, then M03 either cannot see
historical approvals or requires a data migration and a rewrite of every approval site.

**What we build now:** every approval is a row.

```sql
delivery_request_decision (
  id, delivery_request_id, decision APPROVED|REJECTED|RETURNED_FOR_CORRECTION,
  decided_by, decided_at, comment,
  workflow_instance_id uuid NULL   -- always NULL in Phase 1; M03 populates it
)
```

Plus: a **required comment on rejection or return** (the M03 key capability, but it is also just
correct behaviour), and a `RETURNED_FOR_CORRECTION` outcome supported from day one.

**What we do not build:** conditional routing, a task inbox, workflow definitions, versioning of
workflow definitions, escalation.

**The one interface:** approval-requiring use cases call
`approvalPolicy.resolveApprover(context) → { requiredPermission, approverHint }`. Phase 1 ships
`StaticApprovalPolicy`, which reads a threshold from `system_setting` (e.g. "above 30 tonnes needs
`delivery_request:approve_high_value`"). Phase 2 ships `WorkflowApprovalPolicy` implementing the same
port. **One interface, one method, one Phase 1 implementation that does real work.** That passes the
test; a full engine does not.

### Seam 4 — Customer holds as a policy, not an if-statement

**Why it cannot wait:** M14 must refuse scheduling for "a customer blocked by an expired document or
an overdue balance", and M17 must block dispatch for "a customer with an outstanding balance beyond
terms". The _financial_ half of both rules is Phase 2. If Phase 1 inlines
`if (customer.hasExpiredDocument)` at four call sites, Phase 2 edits four call sites.

**What we build now:**

```ts
// src/modules/customers/application/ports/customer-hold.port.ts
export interface CustomerHoldPolicy {
  evaluate(customerId: CustomerId, action: HoldableAction): Promise<HoldResult>
}
export type HoldableAction = 'SUBMIT_DELIVERY_REQUEST' | 'SCHEDULE_PROCESSING' | 'DISPATCH'
export type HoldResult =
  | { blocked: false }
  | {
      blocked: true
      reasons: Array<{ code: string; message: string; overridableBy?: PermissionCode }>
    }
```

Phase 1 implementation: `DocumentComplianceHoldPolicy` — checks expired mandatory KYC documents and
manual administrative holds (`customer_hold` table, with reason and expiry). Real, useful, required
by M08's key control.

Phase 2: `CompositeHoldPolicy([DocumentComplianceHoldPolicy, CreditHoldPolicy])`. Zero changes at
any call site.

**What we do not build:** credit limits, payment terms, receivables ageing, any financial concept.

## 7.2 Seams that are cheap and worth taking

| Seam                                                             | Built in Phase 1                                                                | Enables                                                                                                    |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| **Versioned API** `/api/v1/`                                     | Route structure + `withRoute()` + problem+json + idempotency keys               | M22 mobile app (P2) attaches without restructuring; a v2 can coexist                                       |
| **`NotificationChannel` port**                                   | `EmailChannel` only                                                             | SMS/push/in-app (P2), M28 assistant-drafted replies (P3)                                                   |
| **`FileStorage` + `FileScanner` ports, `file_link` polymorphic** | S3-compatible storage, ClamAV                                                   | M05 document management + e-signature (P2) attaches to invoices/contracts with no schema change            |
| **`AcceptanceSignature.method` enum**                            | `PORTAL_CLICK`, `WET_INK_SCAN`                                                  | M05's cryptographic e-signature adds `E_SIGNATURE` as a third value, plus a nullable certificate reference |
| **`DocumentRenderer` port**                                      | React-PDF                                                                       | Swap engine; M21 (P2) report exports reuse it                                                              |
| **`PlacementStrategy` port**                                     | Best-fit heuristic                                                              | M26 (P3) AI placement recommendation is a second implementation                                            |
| **`branch` dimension on operational tables**                     | One column, one FK, seeded with a single branch                                 | A second EthioStar site never requires an operational-table migration                                      |
| **Effective-dated master data** (§4.2)                           | `bag_type_version`, `piece_rate_version`                                        | M10 tariffs (P2) follow the identical pattern; historical documents stay correct                           |
| **Read-model query layer** (`*.query.ts` returning DTOs)         | Portal dashboard + operational worklists                                        | M21 dashboards and BI (P2) extend the same layer instead of querying entities                              |
| **`locale` on notifications and printed documents**              | Stored per record                                                               | M28 (P3) customer assistant answers in the customer's language                                             |
| **`correlation_id` / `causation_id` on events and movements**    | Set everywhere                                                                  | Phase 3 traceability requirement: "each answer carries a link to the underlying records"                   |
| **Metrics + structured logs with `useCase` labels**              | From day one                                                                    | M21 operational dashboards, M27 anomaly baselines                                                          |
| **Supabase Realtime, enabled on three tables**                   | Publication configured; used only for the receiving, gate and occupancy screens | M21 live dashboards (P2), M22 mobile push-style updates (P2)                                               |

### A note on Realtime

Supabase Realtime is a genuine capability the previous design did not have, and the temptation is to
adopt it broadly. Don't. Phase 1 enables it on exactly three read models where a human is watching a
screen while someone else changes the data — the receiving bay, the gate, and room occupancy.

It is **not** a general data-fetching mechanism: it bypasses the use-case layer, so authorization
becomes RLS-only, and it multiplies connection count. Every other screen stays request/response. If
Phase 2's M21 wants live dashboards, it extends this narrow, understood usage rather than inheriting
a codebase that already uses Realtime everywhere.

## 7.3 Seams we are deliberately NOT building

Recording these prevents the "why didn't we…" conversation in six months, and prevents someone
adding them out of a vague sense of future-proofing.

| Not building                          | Why not                                                                                                                  | What Phase 2/3 does instead                                                                                               |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| Generic workflow engine               | Two approval points in Phase 1. A general engine built against two examples will be wrong for the ten M03 actually needs | M03 builds it against real requirements; the `ApprovalPolicy` port and decision rows are the only pre-work needed         |
| `tariff` / `price` / `invoice` tables | Pricing rules are unknown until the M10 workshop. Guessed schema is worse than no schema                                 | M19/M20 create their tables and add nullable FKs into Phase 1 tables (additive)                                           |
| Plugin/extension registry             | Nothing needs to be extended by a third party. Speculative generality                                                    | —                                                                                                                         |
| Event sourcing                        | State-plus-event-log gives the audit and history benefit at a fraction of the complexity                                 | —                                                                                                                         |
| Message broker (Kafka/RabbitMQ)       | One database, one worker, plant-scale volume. Adds an operational component to run                                       | Postgres queue scales far past this workload; swap behind the `Queue` port if ever needed                                 |
| GraphQL layer                         | The only consumers are our own UI and a future mobile app, both server-rendered or REST                                  | M22 uses `/api/v1`                                                                                                        |

| Abstract `ReportEngine`               | M21's requirements (ad-hoc builder, role-based dashboards) are not knowable now                                          | M21 builds on the read-model query layer                                                                                  |
| AI abstraction layer                  | Building an LLM abstraction 18 months before the first LLM call guarantees the wrong abstraction                         | M24 designs against the actual models available then; it consumes `domain_event` and the query layer, both of which exist |
| Offline sync                          | Explicitly out of scope in the document ("The mobile application requires connectivity")                                 | —                                                                                                                         |

## 7.4 What Phase 2 will actually do, per module

A concrete forecast, so the seams above can be checked against it.

**M03 Workflow & Approval Engine** — new tables (`workflow_definition`, `workflow_instance`,
`workflow_task`). Implements `ApprovalPolicy`. Populates the existing nullable `workflow_instance_id`
on decision rows. Adds a task-inbox UI. _No Phase 1 use case changes._

**M05 Document Management & e-Signature** — extends `stored_file` with retention and classification
columns (additive); adds `signature_certificate`; adds `E_SIGNATURE` to the acceptance method;
builds a document explorer over the existing `file_link`. _No Phase 1 schema restructuring._

**M10 Contract, Tariff & Service Agreement** — new tables following the effective-dated pattern from
§4.2. Adds nullable `contract_id` to `customer` and `delivery_request`. Registers `CreditHoldPolicy`
into the composite hold policy. _One additive migration into Phase 1 tables._

**M19 Billing & Receivables** — new tables. Subscribes to existing domain events. Backfills charges
for Phase 1 history by replaying `domain_event`. Adds `CreditHoldPolicy`. _No Phase 1 code changes
beyond registering a subscriber._

**M20 Storage & Demurrage** — consumes `lot.storage_start_date` and `dispatch.departed_at`, already
recorded. Computes dwell time from the ledger. _Pure addition._

**M21 Reporting & BI** — read-only. Materialized views + the existing query layer. Adds a
report-definition table for the ad-hoc builder. _Pure addition._

**M22 Mobile** — consumes `/api/v1`. Adds token-based auth for mobile clients alongside cookie
sessions (an additional `AuthenticationScheme` in `server/auth`) plus device registration. _The
route structure and use cases are reused unchanged — this is the payoff for versioning the API in
Phase 1._

**Phase 3 (M24–M28)** — reads `domain_event`, the query layer and the ledger. Writes only to its own
tables. The governance requirements ("permissions enforced before the answer is formed", "the AI
never writes to the record on its own authority", "graceful degradation") are satisfiable precisely
because authorization is centralised in `requirePermission` and the AI layer is a _consumer_, never
a participant, in the write path.

## 7.5 The rules that keep the seams open

Add these to the code-review checklist. Each one, violated, closes a seam quietly.

1. **No module writes another module's tables.** Cross-module effects go through that module's
   public use case or through an event. Enforced by the boundaries lint rule.
2. **No business logic in a Server Action or route handler.** If M22 has to reimplement a rule
   because it lived in an action, the seam has failed.
3. **Every state change emits an event.** A silent write is a hole in Phase 2's billing and Phase
   3's history.
4. **Every quantity is recorded in both kg and kesha.** Deriving one from the other later loses the
   count that labour pay depends on.
5. **Never delete; always transition status.** Phase 3 anomaly detection over a table with holes is
   worthless.
6. **Snapshot what you print.** Master data will change; printed history must not.
7. **New enums that the business might extend go in lookup tables**, not `CREATE TYPE`.
8. **Additive migrations only** into tables that already exist in production (§4.6 expand/contract).
