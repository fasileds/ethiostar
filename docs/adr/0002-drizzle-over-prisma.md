# 0002 — Drizzle ORM with hand-reviewable SQL migrations

**Status:** Accepted · 2026-08-12 · **amended by [0013](0013-supabase-as-database-platform.md)**

> **Amendment (Supabase).** Drizzle is retained, over a **direct Postgres connection** — not
> PostgREST and not `supabase-js` for data access, which cannot express this schema's recursive CTEs,
> exclusion constraints and partitioned append-only queries. Three mechanical changes:
>
> - **Migrations are run by the Supabase CLI** from `supabase/migrations/`. SQL is still generated by
>   `drizzle-kit` and hand-reviewed; only the runner and the filename convention change
>   ([04 §4.6](../architecture/04-database-and-migrations.md)).
> - **`prepare: false`** on the driver when connecting through Supavisor's transaction pooler
>   (port 6543). Missing this produces confusing intermittent failures.
> - Drizzle's `pgPolicy` / `authenticatedRole` / `anonRole` / `serviceRole` helpers are used so RLS
>   policies live beside the table definitions.

## Context

The schema needs features that sit outside the comfortable centre of most ORMs:

- append-only enforcement via triggers and `REVOKE`,
- row-level security policies,
- `EXCLUDE USING gist` constraints (appointment overlap, effective-date ranges),
- partial and expression indexes,
- recursive CTEs (lot lineage, coffee passport),
- table partitioning on the append-only tables,
- exact `numeric` handling with no float coercion anywhere.

Migrations must also be reviewable line by line, because a bad migration against `stock_movement`
during harvest is an outage.

## Decision

**Drizzle ORM** for schema definition and typed queries. **Plain `.sql` migration files**, generated
by `drizzle-kit` and then hand-edited and reviewed. Numeric columns configured to return strings and
mapped into `Weight`/`Money` value objects.

## Consequences

**Positive**

- What is reviewed is exactly what runs. No generated intermediate step to reason about.
- Raw SQL is a first-class citizen, so triggers, RLS and CTEs need no escape hatch.
- Thin runtime, no separate engine binary, no generate step in the container build.
- `drizzle-kit check` detects drift between schema definition and migrations in CI.

**Negative**

- Less scaffolding than Prisma: relations, migrations and seeds are more hand-written.
- Smaller ecosystem and fewer worked examples for unusual cases.
- The team must be comfortable reading SQL. For this schema that is a requirement anyway.

## Alternatives rejected

- **Prisma.** Excellent DX and a mature migration story; genuinely viable. Rejected because custom
  SQL lands in `migrations/*/migration.sql` escape hatches that the schema file then does not
  describe, and the resulting divergence is exactly what we are trying to avoid on the tables that
  matter most. If the team's Prisma experience is decisive, switching is contained: `src/db/schema/`
  and `src/modules/*/infrastructure/` change, and nothing else — which is itself a benefit of the
  layering.
- **Raw SQL + a query builder (Kysely).** Maximum control, but loses the single schema definition
  that keeps types and database in agreement.
- **TypeORM / Sequelize.** Weaker TypeScript inference; active-record patterns pull business logic
  into entities and undermine the domain layer.
